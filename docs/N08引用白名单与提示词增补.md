## 一、故障现象（线上实测）

一次正常的提问（`江苏有哪些光伏企业值得关注？`，2023）返回：

```
engine = langgraph | workflow = https://kmj3bsz4kj.coze.site | status = validated
orbs = 3      ← 全部是 product 类型，0 个 evidence 类型
blocks = 6，全部 refs = []
recs: r1/r2/r3 的 evidence_refs 全部 = []
warnings:
  后端校验注记：[bad_ref] 引用不存在或无权访问，已移除：ev:filter_explanation
  后端校验注记：[bad_ref] 引用不存在或无权访问，已移除：ev:item:300827
  后端校验注记：[bad_ref] 引用不存在或无权访问，已移除：ev:item:002150
  后端校验注记：[bad_ref] 引用不存在或无权访问，已移除：ev:item:301278
```

**用户可见后果**：回答正确、数字真实，但**点不出「原文依据」光球**，只剩「产品依据」。
而「每条结论可回溯到年报原文」是本项目的核心卖点（创新点三），这条路上它是断的。

## 二、根因（精确到函数，两层）

### 第 1 层：模型把「字段名」当成了「引用」

`search_companies` 的响应是：

```json
{ "total": 12, "page": 1, "page_size": 5,
  "items": [ { "scode": "300827", "coname": "上能电气", ... } ],
  "filter_explanation": "…" }
```

模型看到响应里有 `filter_explanation` 这个键、以及 items 里的 `scode`，于是臆造出
`ev:filter_explanation`、`ev:item:300827` 这类**格式像、但不存在**的引用。

后端 `server/analysis_service.py` 的校验链把它们正确地拦下了：

- `_collect_valid_refs()` → `_ref_ok()` → `tools.get_evidence()`
- `get_evidence` 要求 evidence 引用**恰好 3 段**（`chunk_id:claim_number:text_version`），
  且 `chunk_id` 必须真实存在于 kb 快照 → 失败
- `_log_bad_ref()` 记 `bad_ref` 并从 `answer_blocks[].refs` / `recommendations[].evidence_refs` 中剥离

**这一步是对的（防线有效），副作用是引用全空。**

### 第 2 层（关键）：引擎自带「不完整的光球列表」，抑制了后端兜底

`server/analysis_service.py:537`：

```python
if not clean.get("orbs"):
    clean["orbs"] = _default_orbs(clean)     # 只在草稿完全没有 orbs 时才补
```

而 `_default_orbs()` 的证据球只从 `answer_blocks[].refs` 里取 `ev:` 开头的引用。

于是形成死结：
1. 引擎输出了 3 个 product 光球 → `clean["orbs"]` **非空** → 兜底**不执行**；
2. 即使执行，`answer_blocks[].refs` 已被清空 → 也建不出证据球。

**结论：只输出「部分光球」比完全不输出更糟——它让后端失去了补救机会。**

## 三、引用协议速查（必须逐字复制，不得改写）

后端 `server/schemas.py` 定义 7 类引用，`parse_ref()` 会做别名归一：

| 类型 | 格式 | 校验规则（`_ref_ok`） |
|---|---|---|
| 原文证据 | `ev:<chunk_id>:<claim_number>:<text_version>` | `chunk_id` 必须在快照中存在；`claim_number` 必须是该块的**真实主张号**；`text_version` 必须与快照一致（不一致会被标 `stale_text`，不伪造高亮） |
| 指标 | `metric:concentration:<scode>:<year>:<CustomerConcentration｜PurchaseConcentration>` | 目前**只支持** `concentration` 表与这两个字段名；该 scode/year 行必须存在 |
| 产品 | `product:<product_id>` | `product_id` 必须存在于 15 张产品卡 |
| 分析 | `analysis:<analysis_id>:<recommendation_id>` | analysis 必须已入库 |
| 对比 | `compare:<comparison_id>` | 本次 `compare_companies` 调用刚生成的 ID |
| 地区 | `regional:<source_id>:<doc_id>` | 必须在该经理**授权地区**内（越权即失败） |
| 企业 | `company:<scode>:<year>` | scode 必须在 317 家样本内 |

别名前缀（等价，但**建议统一用左边的规范写法**）：
`ev`≡`evidence`、`pr`≡`product`、`an`≡`analysis`、`cmp`≡`compare`、`rg`≡`regional`、`co`≡`company`。

> ⚠️ `ev:` 必须是**四段**。`ev:item:300827`（三段）与 `ev:filter_explanation`（两段）都必然失败。

## 四、白名单来源：哪些工具响应里真的带引用

| 工具 | 携带引用的字段路径 |
|---|---|
| `get_company_context` | `signal_refs[].evidence_ref`（最多 6 条）、`rule_candidates[].product_ref`、`metric_refs.customer_concentration`、`metric_refs.supplier_concentration` |
| `get_evidence` | `ref_id`（回显入参 `evidence_ref`） |
| `get_rule_candidates` | `candidates[].product_ref` |
| `compare_companies` | `compare_ref` |
| `search_product_knowledge` | 产品卡检索结果（含 product 引用，以实际响应为准） |
| `search_regional_knowledge` | 地区资料（含 regional 引用） |
| **`search_companies`** | **不返回任何引用**，只有 `items` 与 `filter_explanation` ← 模型正是在这里臆造引用的 |

### ✅ 更稳的做法：不要按字段名硬编码，而是「递归扫全响应」

工具以后加字段时，按字段名硬编码的白名单会失效。**推荐递归遍历整个工具响应，
收集所有符合引用格式的字符串**——实现无关、不会漏。

## 五、步骤一：N07 提示词增补（可直接粘贴）

在 `coze/prompts/analyze.md` 现有 16 条之后追加（或替换第 8 条）：

```text
【引用规则（硬性）】
1. refs / evidence_refs / product_source_refs / orbs[].ref_id 里的每个值，
   都必须**逐字复制**自本轮工具响应中出现的引用字符串，不得改写、拼接、缩写或自造。
2. evidence 引用的格式固定为四段：ev:<chunk_id>:<claim_number>:<text_version>。
   chunk_id 形如 v21_c00020485，claim_number 是数字，text_version 是快照文本哈希。
3. 严禁把工具响应中的**字段名**或**业务字段**当作引用，例如
   ev:filter_explanation、ev:item:<股票代码>、ev:scode、ev:coname 一律为非法引用。
4. 严禁用股票代码、企业名称、排名序号拼造 chunk_id。
5. 如果某个结论在工具响应里找不到对应的引用，就把该处 refs 留为空数组 []，
   并在正文中说明"该项为规则推断/待核实"，**宁缺毋造**。
6. 不得输出 URL、HTML、脚本或图片链接。
7. orbs 字段的两种合法写法（二选一，不要写半套）：
   (a) 完全省略 orbs，或写成空数组 [] —— 由后端自动补建证据球与产品球；
   (b) 完整给出，并且**至少包含一个 evidence 类型的光球**（kind="evidence"，ref_id 为合法 ev: 引用）。
   只给 product 光球而不给 evidence 光球的"半套写法"会阻止后端兜底，导致页面上没有原文证据可点。
```

## 六、步骤二：N08 引用白名单节点（Python 参考实现）

### 6.1 思路

```
N05 事实检索（插件）─┐
                     ├─→ 累积 seen_refs（本轮所有工具响应里出现过的引用字符串）
N06 资料检索（插件）─┘
                                  │
N07 AI 分析 ─→ draft ─────────────┤
                                  ▼
                    N08 自检/格式整理：按 seen_refs 白名单过滤 draft 的所有引用
                                  ▼
                    N09 输出 analysis_draft JSON
```

`seen_refs` 通过图状态（state）在节点之间传递。

### 6.2 工具函数（可直接用，纯函数、可单测）

> **本节的实现已落地为仓库文件 [`coze/n08_ref_filter.py`](../coze/n08_ref_filter.py)，以该文件为准**，
> 本节代码块仅供离线阅读。该文件自带 `python -X utf8 coze/n08_ref_filter.py` 自测（10/10），
> 并有单元测试 `tests/test_n08_ref_filter.py`（10 项）覆盖伪造引用、非法 `product_ref`、
> 半套光球、非法 `kind`、evidence 段数校验与异常不抛出。直接复制该文件进扣子编程项目即可。

```python
# -*- coding: utf-8 -*-
"""N08 引用白名单：只保留本轮工具响应中真实出现过的引用。

设计要点：
- 不按字段名硬编码，递归扫描整个工具响应，避免工具增字段后失效；
- 只做"存在性白名单"，不判断业务对错（业务校验由后端负责）；
- 过滤是确定性的：不依赖模型是否听话。
"""
import re

# 规范前缀 + 全部别名（与后端 server/schemas.py 的 REF_ALIASES 对齐）
_REF_KINDS = ("ev", "evidence", "metric", "product", "pr",
              "analysis", "an", "compare", "cmp",
              "regional", "rg", "company", "co")

_REF_RE = re.compile(r"^(?:" + "|".join(_REF_KINDS) + r"):\S+$")
# evidence 必须四段且 claim_number 为数字
_EV_RE = re.compile(r"^(?:ev|evidence):[^:]+:\d+:[^:]+$")


def collect_refs(obj, out=None) -> set:
    """递归收集任意工具响应中所有形如引用的字符串。"""
    if out is None:
        out = set()
    if isinstance(obj, str):
        s = obj.strip()
        if _REF_RE.match(s) and (" " not in s):
            out.add(s)
    elif isinstance(obj, dict):
        for v in obj.values():
            collect_refs(v, out)
    elif isinstance(obj, (list, tuple, set)):
        for v in obj:
            collect_refs(v, out)
    return out


def _clean_refs(refs, seen: set) -> list:
    """保留白名单内、且 evidence 格式合法的引用；保持原顺序、去重。"""
    out, used = [], set()
    for r in refs or []:
        if not isinstance(r, str):
            continue
        r = r.strip()
        if r in used or r not in seen:
            continue
        if r.startswith(("ev:", "evidence:")) and not _EV_RE.match(r):
            continue
        used.add(r)
        out.append(r)
    return out


def filter_draft_refs(draft: dict, seen: set) -> tuple[dict, list]:
    """按白名单过滤草稿全部引用。返回 (过滤后的草稿, 被剔除的引用列表)。"""
    dropped = []

    def _note(bad):
        dropped.extend(bad)

    for b in draft.get("answer_blocks") or []:
        before = list(b.get("refs") or [])
        b["refs"] = _clean_refs(before, seen)
        _note([x for x in before if x not in b["refs"]])

    for r in draft.get("recommendations") or []:
        for key in ("evidence_refs", "product_source_refs"):
            before = list(r.get(key) or [])
            r[key] = _clean_refs(before, seen)
            _note([x for x in before if x not in r[key]])
        # product_ref 非法会让后端记 block 级问题并把整次分析降级为 partial，必须一并过滤
        pref = r.get("product_ref")
        if pref and pref not in seen:
            r["product_ref"] = None
            _note([pref])

    orbs = draft.get("orbs")
    if isinstance(orbs, list) and orbs:
        kept = []
        for o in orbs:
            rid = o.get("ref_id")
            if rid and rid not in seen:
                _note([rid])
                continue
            kept.append(o)
        draft["orbs"] = kept
        # 关键：不要留"半套"光球——没有证据球就整段清空，交给后端 _default_orbs 兜底
        if not any(o.get("kind") == "evidence" for o in kept):
            draft["orbs"] = []

    return draft, dropped
```

def n05_facts(state: dict) -> dict:

## 八、红线与注意事项

1. **不得为了让光球变多而伪造引用。** 后端 `_ref_ok()` 会逐条核验存在性与权限，伪造只会换来 `bad_ref` 告警和更差的观感；而且这是"可解释、可审计"卖点的根基。
2. **`recommendations[].product_ref` 非法是 `block` 级**（`analysis_service.py:64-66`），会把整次分析从 `validated` 降级为 `partial`——比 `evidence_refs` 为空更严重，必须过滤。
3. **不要输出「半套」光球**：只给 product 球会让后端跳过 `_default_orbs` 兜底。规则是"要么全空、要么含证据球"。
4. `orbs` 上限 12（后端截断）；`kind` 必须是 7 类之一（`company/evidence/profile/product/compare/analysis/checklist`），非法 kind 会被丢弃。
5. `text_version` 必须与快照一致；不一致时后端会标 `stale_text` 并且**不伪造高亮**——这是有意的保护，不要绕过。
6. 不要输出 URL、HTML、脚本；光球由后端根据合法引用构建。
7. 提示词只是"劝导"，`filter_draft_refs` 才是"保险"。**两者都要做**——只改提示词，模型换个说法又会复发。

## 九、可选的加固（本次不必做）

- 若某轮确实一条合法 `ev:` 都拿不到，可让 N05 在事实检索后**主动调用 `get_evidence`**
  回读关键引文，确保证据链至少有一条可回溯；代价是多一次插件调用。
- 长期方案：把 `filter_draft_refs` 的等价逻辑也放在**后端**（引擎返回后、校验前），
  这样无论用哪个引擎都有一道确定性白名单。当前后端已有存在性校验，已足够兜底。
